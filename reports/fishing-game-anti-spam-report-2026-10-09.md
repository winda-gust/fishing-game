代表例：修正前の金の魚は巻き上げ開始から3250msで解放した時点で張り100%・危険時間330msだったが、3255msには危険時間が0になり、3300msの再押下時は張り98.6%・危険時間0となった。修正後の同じ入力列では3250msの解放時に張り100%・危険時間412.353ms、3300msの再押下時もそのまま保持され、3790msで危険時間900msに達して糸切れになった。旧仕様の即時回復の有無で張りの経過も違うため、解放時点の危険時間は前後で同じ値とは限らない。

原因を確認した箇所は `game-core.js` の `FishingGame.#advanceReeling()`。旧実装は、正の時間だけ離すと直ちに張りを毎秒28ポイント下げ、危険時間を無条件で0にした。さらに暴れ中にも進捗が少し増え、休む間は進捗を維持していたため、短い解放を挟むだけで危険を避けて進捗を積み上げられた。

`app.js` の `press()`・`release()`・`syncTime()`・入力イベント処理も確認した。押下・解放前に同じ時計を同期し、物理入力後のclick、キーリピート、重複解放を区別していた。独立した二重入力・時間の二重加算の不具合は確認されず、今回は物理的な回復・危険解除の仕様を主な原因として修正した。入力を回数で無視する処理は追加していない。

## 3. 実装内容と最終調整値

| 項目 | 最終値・挙動 | 採用理由 |
| --- | --- | --- |
| 継続休憩の回復待ち `CONFIG.restDelayMs` | 300ms | 短い解放の回復を防ぎ、予兆で休む操作と150～250msの反応遅れでも全魚が成功したため初期案を維持 |
| 回復速度 `CONFIG.restRelief` | 毎秒28％ポイント | 従来値を維持。300msを超えた部分だけに適用 |
| 危険解除 `CONFIG.safeTension` | 実際に離して回復し、張り70%以下に達した時 | 100%付近のわずかな低下では危険を解除しない。継続休憩で安全を取り戻せる初期案を維持 |
| 糸切れ猶予 `CONFIG.breakGraceMs` | 900ms | 従来値を維持。張り100%で巻いた時間だけ累積 |
| 食いつきの猶予 `CONFIG.reactionMs` | 1800ms | 従来仕様を維持 |

離すと巻く動作と巻くことによる張り増加は即停止する。300ms未満の休憩を足し合わせて回復せず、実際に巻き直すと次の回復待ちは0から数える。300msちょうどでは回復量0、301msで28×0.001＝0.028ポイントだけ回復する。待ち時間を遡ってまとめて回復しない。

危険時間は離している間には増えず、300msの回復待ち中に糸切れにならない。700ms使って10ms離した後も700msを保持し、再び張り100%で巻ける猶予は200msのまま。張りが99.972%になっても保持し、70%以下へ休んで下げた時に解除する。画面の警告と残り猶予も解除まで残す。

暴れ中に巻くと、経過時間に比例して釣り上げゲージを戻す。予兆中の巻き上げ45%は従来どおり。休むだけなら、暴れ中も進捗は減らない。

短いミスで全進捗を失わず、強い魚ほど状態を見て休む利点が増す量を設定した。比較結果が合否条件を満たしたため、300ms・70%と上記後退速度を再調整せず採用した。

新しい休憩時間をスナップショットへ渡し、回復待ち・回復中の案内を画面に追加した。時間処理は回復開始、70%解除、魚状態、ゲージ0/100、900msの境界で分割する。合わせ・再開の押下を保持している間は中立状態で、巻きも回復も行わない。非表示・停止中も回復待ちと危険時間を保持し、重複解放・同一時刻の入力では回復しない。リセット・再挑戦では新状態も初期化する。

ユーザーがPCで修正版を確認する場合は、Node.js/npmとPython 3を用意し、修正ブランチを別フォルダに取得する。

```sh
git clone --branch fix/reeling-anti-spam https://github.com/winda-gust/fishing-game.git fishing-game-review

```

同じPCのブラウザでポート8000を開く。GitHubのHTML表示はコード表示であり、スマホのChatGPT入力欄にコマンドを貼っても起動しない。スマホのlocalhostはクラウド環境を指さない。現時点でスマホから開ける既存公開サイトは今回の連打対策を含まない。main・公開への反映は報告後のユーザー判断を待つ。
